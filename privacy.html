Privacy information for Google sign-in.

Scope of this draft

This static website does not provide login, request Google identity data, set site tracking cookies, or run analytics. The authentication described below is an opt-in, local Google OIDC laboratory profile in the separate VerifAI software repository. The repository does not establish the practices of a future public deployment or those of the website host.

The Google Calendar OAuth laboratory is a separate optional integration with a different OAuth client and scope. Its data handling needs its own deployment review before any public use.

Identity data requested and used

The Google Web OIDC profile requests the openid email scopes and explicitly requests the ID token's auth_time claim. The code checks signed issuer, audience, subject (sub), nonce, issue and expiry times, and authentication age. Email may be included by Google under the requested scope, but the VerifAI authorization code uses the verified sub with a separate administrator-managed issuer/subject binding. It does not use a token email address as a permission or tenant identifier.

Verified subject

Used to look up an administrator-managed tenant binding and approver grant.

Session state

Issuer, subject, tenant, nonce, encrypted short-lived ID token and hashed opaque session ID are stored by the browser host.

Google may process the sign-in request as the identity provider. [CONTROLLER TO CONFIRM GOOGLE TERMS, ROLE AND DATA FLOW FOR ACTUAL DEPLOYMENT].

Why the profile authenticates

The experimental browser host uses a verified human identity to establish a short-lived session and, with an administrator-managed grant, allow an explicit approve or reject decision for a pending exact action. An unknown Google subject is denied; the lab can record a verified enrollment candidate for separate administrator review, without creating a session or granting approval permission. The software does not infer VerifAI privileges from Google email, token scopes or roles.

Cookies and persisted records in the experimental host

The optional browser host uses an opaque HTTP-only session cookie and a separate login-flow cookie. Its private SQLite store holds hashes of session IDs, an encrypted short-lived ID token, issuer, subject, tenant, nonce, expiry and revocation state. It also keeps one-use login-flow and action-presentation state plus metadata-only login and consent events; the event table stores a hash of a subject when present. The lab stores a verified issuer/subject candidate and administrator-managed binding and grant in private files. No raw cookie value or ID token is stored in the session database.

These are properties of the application host code, not cookies or storage on this static site. A real deployment must document its actual storage location and operators: [DEPLOYMENT DETAILS TO COMPLETE].

Configured technical limits and retention gaps

The code gives login flows a 180-second expiry. Browser sessions expire no later than 300 seconds after creation, and sooner if the ID token or authentication-age bound expires. In the opt-in lab, the verified candidate must be no older than 15 minutes for initial binding and grant; its binding and grant expire after one hour. Expiration prevents use, but it is not proof of deletion. The code does not define a complete deletion schedule for expired or revoked session rows, consumed presentations, metadata events, candidate files or backups.

Recipients, hosting and transfers

The local lab contacts Google to perform OIDC login and token verification. The code does not show a public hosting arrangement, processor list, international transfer assessment or operational access policy for a future service. This website is intended for GitHub Pages hosting; the operator must review GitHub's applicable hosting data practices separately.

Revocation, deletion and requests

The browser host's logout revokes its session. The lab's operator command disables its client secret, binding and approver grant, then marks persisted sessions revoked; lab cleanup removes that lab's disposable containers and volumes, but does not remove the operator's source OAuth or TLS files. Revocation is not the same as erasure of every record, and an already issued approval may remain valid until expiry under the documented conditions.
