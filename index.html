01 / THE PROBLEM

A proposed action is not permission.

An AI agent can draft an email, schedule an event or propose another external action. The generated tool call may look valid, but its contents and claims of approval remain untrusted.

For a protected operation, a separate trusted path must decide whether the exact action is allowed and enforce that decision where the external capability lives. If the agent can use the same credential directly, the control can be bypassed.

03 / VERIFIED BUILDING BLOCKS

Controls with explicit boundaries.

Implemented mechanisms are described at the scope demonstrated in the project, with laboratory routes identified as such.

01 / DECIDE

Deterministic policy evaluation

Versioned action fingerprints and separately supplied policy bundles produce bounded, repeatable decisions. The decision itself is not an execution capability.

Documentation ↗
02 / VERIFY

Trusted context & provenance

A verified local path checks signed context and policy-release provenance against host configured keys and exact policy pins.

Documentation ↗
03 / APPROVE

OIDC identity & human approval

A configurable OIDC verifier validates signed identity tokens. The guarded path binds signed approval to the canonical action; a browser-host demo uses a simulated identity provider and explicit consent.

Documentation ↗
04 / ENFORCE

Gateway & replay claim

The local gateway blocks non-allow decisions from its sandbox adapter. A durable SQLite claim prevents a previously claimed operation from being dispatched again in guarded demos.

Documentation ↗
05 / ISOLATE

Separated capabilities

Linux-only routes put synthetic credentials or markers behind a distinct executor identity and peer-authenticated IPC. An opt-in real Calendar connector is still a laboratory profile.

Documentation ↗
06 / ASSESS

Audit & reconciliation

A synthetic provider demo separates signed effect evidence from a hash-linked audit store and supports read-only reconciliation after an uncertain response.

Documentation ↗

04 / SECURITY BY DESIGN

Trust belongs at the boundary.

The design keeps proposals, decisions, approval, credentials and outcome evidence in distinct roles. Its security depends on the deployment honoring those boundaries.

Inspect security invariants ↗
  • 01
    Separation of responsibilities

    Agent supplied fields do not establish identity, policy or consent.

  • 02
    Deterministic policies

    The same canonical action and policy inputs yield the same evaluation.

  • 03
    Bound, single-use approval

    Signed approval identifies the action; guarded claims resist repeated dispatch.

  • 04
    Credential isolation & evidence

    Distinct executor and independent audit mechanisms exist in scoped demonstrations.
